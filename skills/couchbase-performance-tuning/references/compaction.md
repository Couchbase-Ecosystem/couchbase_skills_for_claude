## What compaction does

Couchbase accumulates dead space as documents are deleted and superseded. Compaction reclaims it.

**Couchstore compaction** rewrites data files. While a file is being compacted, the original and the new copy both exist, so disk usage rises temporarily and both read and write I/O are generated by the compaction pass itself.

**Magma compaction** reclaims space against a fragmentation target as well, but is configured differently — see [Magma and compaction](#magma-and-compaction) below. The key operational difference is that Magma's compaction cannot be confined to a time window.

Compaction settings can be set cluster-wide (global auto-compaction defaults) or overridden per bucket.

## Compaction impact on performance

While compaction runs on Couchstore buckets you should expect:

- Additional disk I/O, because compaction both reads the existing data and writes the compacted copy
- A temporary increase in disk space use, because both copies exist until the pass completes
- Some additional CPU on Data service nodes

The magnitude depends on data size, fragmentation level, storage throughput, and how many files compact concurrently — measure it on your own cluster rather than planning against a fixed multiplier.

When compaction saturates disk I/O, the symptoms surface elsewhere:
- KV write latency rises as the disk queue backs up
- Query latency rises if Index shares the same devices
- XDCR falls behind as replication reads compete with compaction writes

Correlate the latency window against compaction activity before concluding compaction is the cause.

## Auto-compaction settings

Configure per bucket or as cluster-wide defaults:

```python
admin_bucket_update(
    name="orders",
    auto_compaction_defined=True,

    # Fragmentation percentage that triggers compaction. Valid range 2-100.
    database_fragmentation_threshold_percentage=30  # illustrative, not a documented default,
    view_fragmentation_threshold_percentage=30      # illustrative, not a documented default,

    # Or an absolute fragmentation size in MiB (whichever triggers first)
    database_fragmentation_threshold_size=1024,

    # Time window - Couchstore buckets only, see below
    compaction_period_from="01:00",
    compaction_period_to="05:00",

    # Abort if compaction is still running when the window closes.
    # Documented default: off (compaction completes past the window).
    abort_outside_compaction_period=True,

    # Run database and view compaction in parallel.
    # Documented default: off.
    parallel_db_and_view_compaction=False,

    cluster="prod"
)
```

Notes on the values above:

- **Fragmentation percentage has a documented valid range of 2–100.** The docs do not publish a single default value for it — the cluster-level value applies unless a bucket overrides it, and Couchbase's own REST example shows 50% for the database threshold. **Read the current value off your own cluster before changing it** instead of assuming.
- `--enable-compaction-abort` and `--enable-compaction-parallel` are both documented as off (`0`) by default.
- If no time period is specified, "the compaction will run at any time of the day."
- The metadata (tombstone) purge interval is a separate setting with a documented range of 0.04 to 60 days. The published default differs between the REST and CLI reference pages, so check the live value on your cluster rather than relying on either figure.

Sources: https://docs.couchbase.com/server/current/manage/manage-settings/configure-compact-settings.html and https://docs.couchbase.com/server/current/cli/cbcli/couchbase-cli-setting-compaction.html

## Tuning compaction for production

**Fragmentation threshold**

The tradeoff is fixed even though the numbers are workload-specific:

- Too low: compaction runs frequently and spends I/O reclaiming small amounts of space
- Too high: dead space accumulates, disk use grows, and reads work across more fragmented files

Change it in one direction at a time and watch both disk use and KV latency before and after. Do not lower the threshold in response to a disk-space alert without checking whether the extra compaction I/O will cost you more in latency than the space is worth.

**Time-window compaction (Couchstore only)**

For latency-sensitive applications on Couchstore buckets, confine compaction to a low-traffic window using `compaction_period_from` / `compaction_period_to`, and set `abort_outside_compaction_period=True` so a long pass does not bleed into peak hours. Choose the window from your own traffic profile.

Be aware of the failure mode: if the window is too short to keep up with the fragmentation rate, fragmentation ratchets upward release after release. Check that compaction is actually completing within the window.

**Parallel compaction**

`parallel_db_and_view_compaction=True` runs database and view compaction at the same time. It finishes sooner at the cost of more concurrent I/O. It is off by default. Leave it off on I/O-constrained nodes.

**Manual trigger**

```python
admin_bucket_compact(bucket="orders", cluster="prod")
```

Triggers compaction outside the scheduled window. Useful after bulk deletes or large batch updates that spike fragmentation suddenly.

## Magma and compaction

Magma buckets are configured differently from Couchstore buckets, and the UI reflects this: "The fields you see depend on the storage backend you selected."

- Magma exposes a **Magma Fragmentation Percentage** setting. The Web Console shows 50% in this field; the documented valid range is 10–100.
- **The time-interval setting does not apply.** Per the docs, the Time Interval section "only appears for buckets using the Couchstore storage engine. It does not appear for Magma buckets." You cannot schedule Magma compaction into a maintenance window — plan for its I/O to be present during peak hours.
- Magma may use more disk space than Couchstore for the same dataset, depending on the fragmentation setting. Account for that when sizing storage during a Couchstore-to-Magma migration.
- If Magma's background compaction cannot keep up with the write rate, `ep_diskqueue_drain` will lag `ep_diskqueue_fill`. The fix is storage throughput or write rate, not a compaction setting.

Sources: https://docs.couchbase.com/server/current/manage/manage-settings/configure-compact-settings.html, https://docs.couchbase.com/server/current/manage/manage-buckets/migrate-bucket.html and https://docs.couchbase.com/operator/current/resource/couchbasebucket.html

## Disk space planning

Couchbase does not publish a single multiplier for compaction headroom, and the right number depends on storage engine, fragmentation threshold, and how much of the dataset churns. Plan from these facts instead:

- **Couchstore needs room for a second copy of whatever is being compacted**, because the original and the compacted file coexist until the pass completes. Sizing to the data size alone will fail during compaction.
- **Magma does not create that temporary full second copy**, but can hold more dead space depending on the fragmentation percentage you set.
- Both engines need room for logs and for growth between compaction passes.

Operational rule that does not depend on a multiplier: **keep meaningful free space headroom on data nodes at all times and alert well before the disk fills.** Running out of space mid-compaction causes compaction to fail, and continued failure compounds the problem.

Also relevant to disk planning: documented maximum data per node is 3 TB for Couchstore and 10 TB for Magma (either vBucket configuration).

Source: https://docs.couchbase.com/server/current/learn/buckets-memory-and-storage/storage-engines.html
